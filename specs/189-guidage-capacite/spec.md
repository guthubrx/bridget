# Session189 — Motiver les refus de capacité
Correction de guidage autorisée. Un refus resource_saturated doit conserver les mesures fraîches et seuils réellement évalués, la cible, le code, le request_id et le sort durable, sans changer les critères ni créer une tâche. Un ancien reçu sans ces preuves doit rester explicitement historique et incomplet, sans déduire une saturation actuelle. Cas opus166-correction-saut-planificateur-cartae-20261027-01 : snapshot initial non saturé, refus final sans fait associé. La lecture d605c969 a depuis réussi par le propriétaire et son résultat a été lu/ACK ; cause du refus transitoire non établie, aucun contournement ni modification de cette tâche.

Choix : conserver refusal_code=resource_saturated pour les anciens lecteurs. La preuve fermée est ajoutée au metadata du reçu dans la même transaction CAS que son refus ; elle ne remplace ni le snapshot initial ni son canon. Le premier refus durable conserve sa preuve au rejeu. Aucun seuil ni sélection changé. Si la borne de metadata interdit cette conservation, refuser la transition avec une erreur explicite ; aucun état terminal inventé.
Le précontrôle MCP CallerScope perd aussi le guidage d’un refus d’attestation : corriger uniquement sa projection fermée, sans contexte de tâche avant autorisation.
