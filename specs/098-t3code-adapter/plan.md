# Plan 098 — Adaptateur t3code (révision 2, option A)

Statut : proposé le 2026-09-14, révisé après contre-revue adverse (BLOCKED → corrections 1, 2, 5, 6, 7, 8 et option A pour 3-4). Rust 1.92, trois crates existants. Une dépendance nouvelle arbitrée : `minreq` sans TLS pour le HTTP loopback (aucun client HTTP dans le workspace, cf. reuse-audit.md) ; `uuid` étendu à `v5`. Prérequis de poste : CLI `t3` (npm) pour émettre le jeton ; l'application Electron installée (0.0.40) n'en fournit pas.

## Architecture et réutilisation

1. **`bridget t3 <install|status|uninstall|serve>`** dans `crates/bridget-daemon/src/t3code.rs`, enregistré dans `cli.rs` comme `federate` (096). `install` : (a) `t3 auth session issue --subject bridget --label bridget-<identifiant d'installation unique> --ttl <d> --json` → jeton, identifiant de session, expiration conservés en 0600 dans l'état privé Bridget ; si le reçu JSON est illisible après création, la session est retrouvée par `client.label` dans `t3 auth session list --json` et révoquée avant nouvel essai, jamais laissée orpheline ; (b) enregistrement du service `bridget t3 serve` par le moteur launchd/systemd de 095 ; un manifeste d'installation liste ce qui a été posé ; toute étape ratée défait les précédentes. `uninstall` : révocation par identifiant de session, retrait du service, effacement de l'état. **Aucune modification directe dans `~/.t3`** : ni `settings.json`, ni fichier MCP ; la base d'authentification n'est touchée que par la commande officielle `t3` (v1 sans émission depuis l'agent, donc sans injection MCP).
2. **`bridget t3 serve`**, le pont : lit `~/.t3/userdata/server-runtime.json` (adresse, PID), valide la forme de chaque réponse route par route (`t3code_contract.rs`), sonde `GET /api/orchestration/snapshot` à cadence bornée (10 s au repos, 2 s quand un fil a un tour actif ou une remise en attente), ne relit un fil que si son `updatedAt` ou son `latestTurn` a changé (pas de `threadSequence` en 0.0.40), traite `archivedAt`/`deletedAt` renseignés comme fin de vie, n'accepte que `http://127.0.0.1:<port>` reconstruit depuis le port publié (origine non locale, fichier périmé ou PID absent = refus nommé), tient une connexion daemon par fil ouvert (Register `protocol = t3code`, `PresenceMode::Cli`, `agent_id` = UUID v5 du `threadId` dans un espace Bridget fixe, `instance_id` dérivé, domaine = dossier du fil), `JournalReady` avec un `JournalWriter` par fil, désenregistrement à l'archivage. Reçoit `DeliverIdempotent` et le confie à une **file par fil servie par un worker dédié** : la boucle de connexion ne bloque jamais (le tracker de reçus est consulté immédiatement pour le rejeu ; l'accusé ou l'indéterminé est envoyé par le worker quand le sort est connu). Le worker sérialise les remises du fil : attente de l'absence de `activeTurnId` (borne configurable, défaut 120 s, sondage 2 s), puis `POST /api/orchestration/dispatch` `thread.turn.start` avec `commandId` = identifiant de remise et `messageId` choisi par le pont ; accusé après `DispatchResult` ; 401 → un renouvellement de jeton puis un seul nouvel essai ; déconnexion du daemon pendant l'attente, refus, délai ou panne → indéterminé nommé. Rappels et notifications empruntent la même file. La course résiduelle (tour démarré par l'humain entre l'observation et le `dispatch`) est documentée, détectée après coup par la projection, journalisée, et testée.
3. **Réponse liée renvoyée par le pont, seulement quand elle est prouvée** : la projection du fil retrouve le message du pont par son `messageId` ; la réponse liée est le tour assistant de même rang que le message du pont (k-ième message utilisateur → k-ième tour, FIFO observé en T001, un tour identifié par son `turnId`), attendu jusqu'à `streaming = false` et `latestTurn.state = completed` pour ce `turnId` ; si le rang ne peut être établi (message du pont absent, tours en nombre incohérent, page tronquée avant le message) aucune réponse n'est envoyée : la demande reste ouverte, l'ambiguïté est journalisée et le mécanisme de palier existant s'applique. La **corrélation en attente est durable** (dans le fichier d'état du fil `sessions/<agent>/t3code-state.json`, section `pending` : identifiant de remise et de demande, émetteur, `messageId`, `threadId`), écrite avant le `dispatch`, reprise au démarrage du pont, effacée après réponse ou ambiguïté ; testé : redémarrage après `DispatchResult` et avant la fin du tour.
4. **Journal par différence de snapshots** : un repère d'installation (`sessions/t3code-watermark.json` : instant et séquence de snapshot à l'installation) et, par fil, une séquence durable des messages déjà projetés (même fichier d'état `sessions/<agent>/t3code-state.json`, section `cursor` : identifiants projetés dans l'ordre du fil). Un seul fichier d'état par fil, écrit atomiquement. À chaque passe où `updatedAt` ou `latestTurn` du fil a changé, `GET /api/orchestration/threads/:id` par pages récentes (`turnLimit`, `beforeCursor`), en remontant seulement jusqu'au curseur durable ou au repère d'installation ; projection de tous les messages postérieurs au repère et absents du curseur, dans l'ordre du fil : `turn_start {from:"human"}`, `update {kind:text}`, `turn_end`. Un fil créé et achevé avant le premier passage ou pendant un arrêt du pont est projeté une fois au passage suivant ; identifiants manquants → lacune annoncée. Testé : redémarrage au milieu d'un tour, historique préexistant, fil achevé avant le premier passage, fil créé pendant l'arrêt, tour non causé par Bridget, fil de plus de 2 000 messages, reprise nécessitant plusieurs pages, fil inchangé non relu.
5. **Contrat t3code isolé** : `crates/bridget-daemon/src/t3code_contract.rs` porte routes, champs lus, forme validée de `server-runtime.json` (dont son `version` = format du fichier, pas de l'API), commandes `t3 auth`, et les fonctions de lecture typées ; refus nommé par route et par champ.
6. **Réutilisation** : `deliver_idempotent_to_interactive` et `IdempotentDeliveryTracker` (`pub(crate)`), `JournalWriter`, `AttachRelayWorker`, `connect_and_register_with_domain_at`, script de service 095, schéma de commande 096, harnais Python 090/097.

## Répartition des fichiers

- daemon : `src/t3code.rs`, `src/t3code_contract.rs`, `src/cli.rs`, `src/lib.rs`, `src/wrapper.rs` (visibilités), `Cargo.toml` (`minreq`, `uuid` v5), `scripts/federate-ssh.sh` (entrée de service si réutilisable, sinon script frère minimal arbitré).
- tests : `tests/t3code_098_test.rs` + `tests/fixtures/t3code_server_098.py` (faux t3code : fichier runtime, snapshot, détail, dispatch avec reçus par `commandId`, 401/500/délais, tour actif simulé, archivage) ; unitaires du contrat, du cycle de vie du jeton (JSON, renouvellement borné, révocation) et de la projection de journal ; `tests/features/098-t3code-adapter.feature`.
- docs : README FR/EN, `skills/bridget/SKILL.md` et références, ADR 034.

## Invariants et coût

Un fil = une identité = une connexion daemon = un journal = un curseur. Le pont n'écrit dans t3code que par `dispatch` ; il ne lit que les routes du contrat ; le jeton ne sort jamais de l'état privé. Sondage O(nombre de fils) par passe, une requête au repos, détail seulement sur activité ; remise : attente bornée puis une requête. Aucune trame daemon ni outil MCP nouveaux.

Coût estimé : `t3code.rs` ~500 lignes, `t3code_contract.rs` ~150, faux serveur ~300, test Rust ~300, docs et ADR ~120.

## Gates constitution XIX/XX

- Réutilisation maximale des primitives 089/095/096/097 ; pas de client RPC maison ; pas d'écriture dans t3code.
- Dépendance `minreq` justifiée par écrit ; `uuid` v5 = fonctionnalité d'une dépendance présente.
- Refusé : identité déduite d'une variable d'environnement ; injection MCP dans les agents t3code ; modification de `settings.json` ; fork.
- À vérifier avant tout code (T001) : routes `/api/orchestration/*` et `server-runtime.json` sur l'application 0.0.40 réelle ; sortie JSON de `t3 auth session issue` ; comportement de `dispatch` pendant un tour actif ; forme du détail de fil (identifiants de messages et de tours).

## Validation
