# ADR 014 — Provenance des objectifs avant gate de dette humaine

**Statut** : Accepté pour la tranche 1
**Date** : 2026-08-28

## Contexte

Le système doit empêcher toute nouvelle ouverture automatique lorsqu'une
réponse humaine est due. Aujourd'hui, ni l'objectif ni le ledger ne portent
les faits nécessaires. Les contrôles externes sont contournables et un check
dans la base Bridget suivi d'un commit dans la base le service compagnon laisse une course.

Le chemin de création n'est pas limité à une interface : CLI, guichet et
routines convergent vers deux réservations transactionnelles et une branche
SQL d'insertion commune.

Une sonde de migration v19 emploie aussi textuellement `INSERT INTO objectives`,
mais uniquement sous savepoint avec `ROLLBACK` et contrôle du cardinal
avant/après. Elle n'est pas une ouverture durable ; l'inventaire structurel la
nomme séparément au lieu de la faire disparaître par un filtre de forme.

## Décision

Nous livrons le mécanisme en trois tranches ordonnées.

La première introduit une origine fermée dans chaque objectif et une capacité
opaque `ObjectiveOpeningPermit`. Les ouvertures actuelles sont explicitement
`AutoGenerated`. Les payloads antérieurs sont `LegacyUnknown`, sans migration
interprétative. Les deux réservations et l'insertion neuve exigent le permit,
et une future provenance humaine participe à l'identité canonique versionnée
de la commande. Le canon automatique v2/v3 reste inchangé pour ne pas rendre
divergents les replays déjà persistés.

`HumanRequest` est représentable dans le stockage, mais aucun appelant ne peut
obtenir son permit tant que le daemon n'émet pas une attestation liée au
message humain et au hash de la requête. Nous refusons de transporter une
simple déclaration MCP/CLI : ce serait rendre la preuve forgeable.

L'attestation signe un sujet canonique qui exclut l'attestation elle-même. Les
octets idempotents finaux peuvent contenir cette preuve ; son hash ne se définit
donc jamais récursivement sur un document qui porte déjà ce hash.

La deuxième tranche fera exister l'obligation de réponse dans le ledger. La
troisième projettera cette dette dans le service compagnon et sérialisera sa vérification
avec l'insertion d'objectif.

Cet ordre est une contrainte de sûreté, pas une préférence de déploiement. Un
gate livré avant la voie `HumanRequest` attestée refuserait aussi les objectifs
explicitement demandés par l'humain, puisque tous les producteurs encore
disponibles ne savent émettre que `AutoGenerated`.

## Conséquences positives

- toute nouvelle origine automatique devient comptable ;
- l'histoire inconnue reste honnêtement inconnue ;
- les routines ne contournent pas la frontière ;
- une clé idempotente ne peut pas changer de provenance ;
- la voie humaine ne s'ouvre pas avant sa preuve.

## Conséquences négatives

- la tranche 1 seule ne bloque encore aucune ouverture automatique ;
- les constructeurs et fixtures doivent tous déclarer une origine ;
- la voie `HumanRequest` reste inutilisable jusqu'à la tranche daemon ;
- le déploiement complet nécessite un protocole inter-store conservateur.

## Alternatives rejetées

- **booléen `human=true` fourni par l'appelant** : forgeable ;
- **inférence depuis le texte, `constat_id`, TTY ou principal** : corrélation
  causale non attestée ;
- **absence d'origine égale automatique** : reclasserait 611 objectifs sans
  preuve ;
- **garde seulement MCP/CLI** : contournée par les routines ;
- **script ou ronde** : constate après coup et dépend de la discipline ;
- **check Bridget puis commit le service compagnon** : course TOCTOU ;
- **file prioritaire humaine** : réordonne le travail sans tenir la propriété.
